PO — Product Owner
Quando e como o PO atua
Foco O PO atua antes e durante o refinamento — garantindo que o card chegue ao dev com requisitos claros e critérios de aceite verificáveis. Não precisa usar comandos de implementação ou revisão técnica.
Touchpoints
  • Card novo no backlog: roda /refinar-feature para estruturar a User Story — ou acompanha o dev e atua como aprovador da proposta gerada
  • Antes do desenvolvimento: roda /documentar-e2e para gerar o caderno de testes em linguagem de negócio, usado como base para UAT
  • Card de bug: valida o bug report gerado pelo dev com /identificar-bug antes da correção começar
/refinar-feature <EFC-XXXX>
Como o PO usa O Claude transforma a descrição atual do Jira em uma User Story estruturada (contexto, "Como… quero… para que…", critérios de aceite numerados) e apresenta para aprovação antes de gravar qualquer coisa. Esse é o momento central do PO: revisar, pedir ajustes e confirmar. Só após aprovação explícita a descrição é atualizada no Jira.
Quando usar Ao preparar um card para entrar em sprint — antes do planejamento técnico do dev.
Pré-requisitos Variáveis JIRA_BASE_URL, JIRA_USER e JIRA_API_TOKEN exportadas.
/documentar-e2e <EFC-XXXX>
Como o PO usa Gera um caderno de testes em Gherkin (Given/When/Then) em linguagem de negócio pura — sem código, sem jargão técnico. O resultado é apresentado para aprovação do PO, depois anexado ao card Jira. Serve como contrato de entrega e referência para testes de aceitação (UAT).
Quando usar Após a User Story aprovada, antes ou logo após o início do desenvolvimento.
Pré-requisitos User Story definida no card (ou Docs/user-story-EFC-XXXX.md gerado pelo /refinar-feature). Variáveis Jira exportadas.
Refinamento
/refinar-feature <EFC-XXXX>
O que faz Lê a descrição do card Jira, explora o repositório e redige uma User Story estruturada (contexto, "Como… quero… para que…", critérios de aceite numerados e regras de negócio). Apresenta para aprovação, atualiza o Jira em formato ADF e salva Docs/user-story-EFC-XXXX.md localmente.
Quando usar Primeiro passo quando um card chega ao time — antes de qualquer planejamento técnico.
Pré-requisitos Variáveis JIRA_BASE_URL, JIRA_USER e JIRA_API_TOKEN exportadas.
/documentar-e2e <EFC-XXXX>
O que faz Gera um caderno de testes E2E em Gherkin (Given/When/Then) em linguagem de negócio — sem referências a botões, modais ou endpoints. Cobre caminho feliz, casos de borda e controle de acesso. Apresenta para aprovação, salva em Docs/, anexa ao Jira e remove o arquivo localmente.
Quando usar Durante o refinamento ou antes do início do desenvolvimento. O caderno é insumo para QA validar a entrega sem precisar ler código.
Pré-requisitos Card com User Story definida (ou descrição suficiente no Jira). Variáveis Jira exportadas.
/identificar-bug <EFC-XXXX>
O que faz Lê o card de bug no Jira (incluindo anexos), explora o código e gera dois documentos: um bug report em linguagem de negócio (passos para reprodução, impacto, comportamento esperado) e um caderno de testes E2E com cenário de regressão. Ambos são aprovados antes de serem anexados ao Jira. Garante que o repositório está no master atualizado antes de começar.
Quando usar Ao receber um card de bug — antes de abrir uma branch de correção.
Pré-requisitos Variáveis Jira exportadas. Repositório sem alterações não commitadas.
Planejamento Técnico
/planejar-implementacao <EFC-XXXX>
O que faz Lê o spec (arquivo Docs/user-story-EFC-XXXX.md ou, se não existir, o Jira), explora o repositório e monta um plano técnico faseado respeitando a arquitetura em camadas (Domain → Domain.Services → Infra → API → Frontend). Cada fase é vinculada a um critério de aceite e indica explicitamente quando seguirá padrões de scaffolding. Apresenta para aprovação e salva em Docs/plano-tecnico-EFC-XXXX.md.
Quando usar Após refinamento aprovado, antes de abrir a branch de desenvolvimento. O plano é o guia de execução do /executar-plano.
Pré-requisitos User Story aprovada (preferencialmente Docs/user-story-EFC-XXXX.md gerado pelo /refinar-feature).
Implementação
/executar-plano <EFC-XXXX>
O que faz Lê o Docs/plano-tecnico-EFC-XXXX.md e executa as fases pendentes uma por vez, aguardando confirmação entre elas. Verifica que o branch não é protegido (master, develop, homolog). Ao finalizar, executa build e testes (dotnet test no backend, npm run build + lint no frontend) e cria o commit.
Quando usar Após plano aprovado e branch de feature criado. É o comando central da fase de desenvolvimento.
Pré-requisitos Arquivo Docs/plano-tecnico-EFC-XXXX.md existente. Branch feature/EFC-XXXX-descricao ativo.
/criar-entidade <NomeDaEntidade>
O que faz Scaffolding completo de uma nova entidade de domínio: classe C# (BaseEntity ou StatefulEntity), interface e implementação do repositório, mapping EF Core e fixture de testes com Bogus. Atualiza entidades relacionadas (navegações reversas e mappings).
Quando usar Quando uma fase do plano exige nova entidade, ou diretamente para adicionar uma entidade pontual. Deve vir antes de qualquer service ou filtro que dependa dela.
Inputs Nome da entidade, tipo (Base ou Stateful) e lista de campos com tipos e relações.
/criar-filtro <Funcionalidade>
O que faz Scaffolding completo de um filtro em cascata (ex.: Rede → Escola → Turma): enum de passos, DTO de request, repositório de filtro, FilterService, ValidacaoService, controller com endpoints por passo, configuração Angular do filtro, service Angular e página de listagem (corpo da listagem vazio). Termina com testes de integração do FilterService.
Quando usar Quando a feature inclui uma tela de listagem com filtro hierárquico. Cria toda a estrutura de uma vez — backend e frontend.
Inputs Nome da funcionalidade (PascalCase), passos do filtro em ordem, entidade-base e regras adicionais opcionais.
/criar-exportacao <Funcionalidade>
O que faz Adiciona exportação Excel em uma feature que já possui filtro: DTO de exportação, método GetParaExport no repositório existente, ExportarService, endpoint /export no controller e botão de exportação no componente Angular. Termina com testes de integração do ExportarService.
Quando usar Após o /criar-filtro — é um complemento, não pode ser executado sem o filtro existente.
Inputs Nome da funcionalidade, colunas do Excel, nome do arquivo .xlsx, nome da aba, repositório de origem e campos obrigatórios para exportar.
/criar-service <Funcionalidade> <NomeService>
O que faz Cria a interface (I{Nome}Service) e a implementação ({Nome}Service) de um service de domínio: primary constructor C# 12, ServiceResult<T>, validação procedural, sem Include(), sem queries dentro de loops. Pode ser chamado pelo usuário ou como subagente pelos comandos de scaffolding.
Quando usar Quando a feature requer um service específico que não se enquadra nos padrões de filtro ou exportação.
Inputs Funcionalidade (namespace), nome do service, tipo de retorno, dependências, métodos públicos, regras de validação e lógica de negócio.
/criar-testes <NomeService | Feature>
O que faz Cria ou complementa testes para frontend (Jest) ou backend (.NET integração). No frontend: testes de serviço (mock de ApiClient) e testes de componente (lógica pura extraída, sem TestBed). No backend: classe herdando BaseTest, seed via SeedDatabase, cobrindo caminho feliz, ramificações e variações de permissão. Apresenta os cenários para aprovação antes de criar arquivos.
Quando usar Durante a implementação (coverage de novos services) ou em revisão quando lacunas forem identificadas. O /executar-plano já inclui esta etapa na última fase.
Inputs Nome do service (backend) ou nome da feature/arquivo (frontend).
Revisão de Código
/analisar-pr [branch | nº-PR] [EFC-XXXX | --criterios]
O que faz Analisa o diff entre dois branches e gera Docs/revisao-pr.md com três seções: Conformidade com o Spec (CA por CA), Backend (N+1, projeções, autenticação, UnitOfWork, etc.) e Frontend (tipagem, erros HTTP, standalone, modais, guards).
Quando usar Antes de aprovar um PR — pelo autor (auto-revisão) ou pelo revisor.
Modos de uso
/analisar-pr 212 analisa o PR #212 do GitHub
/analisar-pr master EFC-1234 compara branch atual com master, valida os CAs do card
/analisar-pr master --criterios pede os CAs manualmente antes de analisar
Merge
/merge-branch <branch-origem>
O que faz Traz as mudanças do branch informado para o branch atual, com triagem e resolução de conflitos, build de verificação e commit do merge. Classifica cada conflito entre resolvível automaticamente (imports, formatação, adições independentes) e requer decisão humana (lógica alterada nos dois lados).
Quando usar Para atualizar uma branch de feature com mudanças de develop ou master. Não substitui o merge via PR.
Restrições
homolog nunca pode ser a origem. Merges para production só são permitidos a partir de master.

Comandos internos — não invocar diretamente

Subrotinas chamadas pelos comandos acima
_jira.md Verifica variáveis de ambiente e busca um ticket no Jira via curl.exe.
_jira-handoff.md Baixa o zip de handoff de design anexado ao Jira e extrai em Docs/handoff-{TICKET}/.
_jira-documentar.md Anexa um arquivo ao Jira como attachment e remove o arquivo local em seguida.
_explorar-repositorio.md Orienta o agente a usar a documentação interna e o enum Funcionalidade.cs como ponto de partida.
_git-verificar-sem-alteracoes.md Verifica git status e interrompe o fluxo se houver alterações não commitadas.
_pr-criterios-analise.md Define os critérios de backend e frontend aplicados pelo /analisar-pr.
_pr-resolver-branches.md Resolve BRANCH_ORIGEM e BRANCH_DESTINO a partir dos argumentos do /analisar-pr.
_pr-resolver-criterios.md Obtém os critérios de aceite do arquivo local, do Jira ou do usuário para o /analisar-pr.
